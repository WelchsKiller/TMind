1. ECG 원본 데이터 전송 관련 암호화 방식


질문1. 위 알고리즘 조합(혼합 암호화)으로 앱 측 구현 가능한지

답변: 가능합니다.

■ 제안 구조에 대한 앱 측 의견
  - AES-256-GCM + RSA-OAEP(SHA-256, 3072bit) 조합은 Android에서 구현 가능합니다.
  - 앱에는 이미 AES-256-GCM 구현(AesCrypto)이 있어, CEK 1회용 생성·암호화 부분은 확장하기 쉽습니다.
  - RSA-OAEP-256은 javax.crypto.Cipher(RSA/ECB/OAEPWithSHA-256AndMGF1Padding)로 구현 가능합니다.
  - 전송 JSON(encryptedCek / iv / ciphertext / authTag, Base64URL) + JWT 헤더 형식도 Retrofit multipart/JSON으로 수용 가능합니다.

■ 참고(현재 구현)
  - 현재 HRV 업로드는 암호화 없이 multipart CSV(signal)로 전송 중입니다.
  - 로컬 저장(히스토리·큐)만 AES-256-GCM을 사용합니다.
  - 제안하신 Hybrid Encryption은 서버 배포 스펙에 맞춰 업로드 API에 적용하겠습니다.


질문2. 공개키 전달 방식 — 하드코딩 vs 서버 API 조회 중 선호

답변: 서버 API 조회를 선호합니다.

■ 이유
  - 키 교체(로테이션)·폐기 시 앱 강제 업데이트가 필요 없습니다.
  - 환경(개발/운영)별 키 분리가 쉽습니다.

■ 제안
  - GET /api/member/crypto/public-key (또는 동등 엔드포인트)로 공개키(PEM/Base64) + keyId 조회
  - 앱은 keyId와 함께 encryptedCek를 전송해 서버가 올바른 개인키로 복호화
  - 최초 1회 조회 후 캐시, 업로드 실패(키 만료 등) 시 재조회
  - 하드코딩은 비상용 폴백 정도로만 검토


2. ECG 원본 1회 측정분 용량 / 전송 방식


질문3. ECG 원본 1회 측정분의 대략적인 파일 용량

답변:

■ 측정 스펙
  - 측정 시간: 5분(300초)
  - 샘플링: 250Hz
  - 이론상 원시 샘플 수: 약 75,000개(250 × 300)

■ 용량 추정(원본 전체 전송 시)
  - float32 바이너리: 약 300KB
  - CSV(텍스트): 약 0.8~1.5MB
  - Hybrid 암호화 JSON(Base64URL) 시: CSV 대비 약 1.3~1.5배 → 대략 1~2.5MB

■ 현재 앱 업로드 실태(중요)
  - 현재 서버로 올리는 파일은 5분 원시 전체가 아닙니다.
  - 분석 후 대표 파형(lastSpike, 보통 100~500 샘플)을 CSV로 만들어 전송합니다.
  - 현재 업로드 용량: 대략 수 KB 수준


질문4. 파일 분할 없이 1회 전송으로 진행하는 것이 맞는지

답변: 네, 1회 전송으로 진행하는 것이 맞습니다.

■ 근거
  - 원본 전체라도 보통 수 MB 이하라 multipart 1회 전송으로 충분합니다.
  - 분할 전송은 재조립·누락 처리 복잡도가 커 현재 요구에 불필요합니다.
  - 요청 본문 제한을 5MB 이상으로 두시면 여유 있습니다.


3. 오늘의 화면 필드


질문5. 제공 필드 외에 추가로 필요한 것이 있는지

답변: 안내하신 필드로 기본 연동은 충분합니다. 아래는 있으면 앱 구현이 더 안정적인 항목입니다.

■ 제공 필드 활용 계획
  - currentType: AM/PM/BASELINE/FOLLOWUP — 앱 로컬 시간 판별과 서버 기준 동기화
  - currentSessionId / hrvDone / emaDone / diaryDone: 비정상 종료 후 이어하기
  - eventActive / eventGuideText: 추가 측정 카드 활성·안내 문구 표시

■ 추가 요청(선택)
  1) missedType — 놓친 정기 세션 안내(현재 모델에 필드만 있고 UI 미반영)
  2) participatedDays 또는 studyDayIndex — 7일 정서 추이 버튼 노출(현재는 참여현황 API 사용 중)
  3) eventGuideText 활성 조건 — eventActive=true일 때만 내려주면 됩니다
  4) (가능 시) 서버 기준 오늘 날짜/타임존 — 자정 경계 불일치 방지


4. EMA 설문 valence / arousal 공식


질문6. 사용 중인 공식이 아래와 같은지 확인

답변: 구조(9문항 가중합, 1~5 응답, 별도 역채점 없음)는 동일합니다.
다만 일부 문항의 부호가 질의서 표기와 다릅니다. 앱 실제 가중치는 아래와 같습니다.
(출처: Nandy et al., 2023 / RussellEmotionCalculator.java)

■ 문항 순서(l1~l9)
  l1 happy, l2 frustrated, l3 sad, l4 worried, l5 restless,
  l6 excited, l7 calm, l8 bored, l9 sluggish

■ Valence 가중치(앱)
  +0.89, -0.60, -0.81, -0.07, -0.04, +0.70, +0.78, -0.35, -0.22

■ Arousal 가중치(앱)
  +0.17, +0.40, -0.40, -0.32, +0.29, +0.71, -0.68, -0.78, -0.50

■ 계산
  valence = Σ (Vw_k × lk)
  arousal = Σ (Aw_k × lk)
  lk ∈ {1..5}, 누락 시 산출하지 않음

■ 질의서 대비 차이(확인 요청)
  - Valence: l6(excited), l7(calm)은 앱에서 양수(+0.70, +0.78)
  - Arousal: l3(sad), l4(worried), l7(calm), l8(bored), l9(sluggish)은 앱에서 음수

■ 참고
  - 서버 검증용으로는 위 원시 가중합(스케일 나누기 전)을 사용하시면 됩니다.
  - 사분면 표시용으로만 /5 정규화(EMA_DISPLAY_SCALE=5)를 사용합니다.


5. POST /api/member/session 호출 시점


질문7. AM/PM·이벤트 세션에서 세션 시작 API를 언제 호출하는지

답변: 세션 ID가 아직 없을 때, 해당 세션의 첫 업로드/진행 직전에 호출합니다.
(ensureSessionStarted: 캐시된 sessionId가 있으면 재호출하지 않음)

■ AM / PM (정기 세션, event=false)
  1) 심박변이도 확인(결과 확정) 시점 — HrvResultActivity 확인 버튼
     → POST /api/member/session 후 HRV 업로드·예측 저장
  2) HRV 없이 설문/일기로 바로 진입하는 경우
     → EMA 또는 음성일기 화면 진입 직에도 세션 시작 호출

■ EVENT (추가 측정, event=true)
  - 동일 패턴: 추가 측정 모드에서 HRV 확정 / EMA 진입 / 일기 진입 시
  - StartSessionRequest.event = true

■ 정리
  - 세션 선택 화면에서 미리 시작하지 않습니다.
  - “실제 미션을 시작·확정하는 첫 순간”에 1회 생성하고, 이후 단계(HRV→예측→피드백→EMA→일기)는 같은 sessionId를 재사용합니다.


6. 음성일기 용량 및 최대 시간


질문8. 최대 3분이 확정인지, 대략 파일 용량은?

답변:

■ 최대 시간
  - 현재 앱 기준 최대 3분(180초)으로 구현·확정되어 있습니다.
  - 화면 문구와 코드(MAX_SEC = 180)가 동일합니다.

■ 녹음 스펙
  - 포맷: MPEG-4 / AAC
  - 샘플레이트: 16kHz
  - 비트레이트: 64kbps

■ 용량 추정
  - 최대 3분: 약 1.4MB (64,000 bit/s ÷ 8 × 180초 ≈ 1.44MB)
  - 실제 사용은 보통 30초~2분대 → 약 0.2~1.0MB


7. 수정 기능


질문9. 완료 미션 수정 기능이 임의인지, 확정인지

답변: 앱 UI상으로는 의도적으로 넣어 둔 기능입니다(확정 방향).
다만 서버 수정 API가 없어, 현재는 로컬 재작성 위주이며 서버 재전송은 연결되어 있지 않습니다.

■ 현재 앱 동작
  - 홈에서 완료된 설문/일기 카드를 누르면 수정 확인 후 재진입 가능
  - editMode=true로 진입
  - EMA/음성일기 수정 결과는 로컬 큐·히스토리에만 반영
  - 서버 submitEma / uploadVoiceDiary 호출은 editMode에서 생략

■ 정리 및 요청
  - 제품 요구상 “완료 후 수정”은 유지하는 방향입니다.
  - 서버에 수정(또는 재제출) API가 준비되면 앱에서 연동하겠습니다.
  - 수정 불가(완료 후 잠금)로 정책을 바꾸실 경우 알려주시면 UI에서 제거하겠습니다.
